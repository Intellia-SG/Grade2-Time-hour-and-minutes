1. System Architecture Overview
1.1 Architectural Goals
The Time: Hours & Minutes platform must support a media-heavy, animation-rich, audio-synchronized single-concept learning experience for young children, while remaining performant on low-to-mid-range tablets globally. The architecture is designed around the following goals:
Fast initial load (<3s on 4G) with progressive asset streaming
Modular content architecture allowing independent module deployment
Offline-first capability for classroom use with unreliable internet
Strict COPPA/GDPR-K compliance for child data privacy
Scalable to millions of concurrent sessions across global regions
Decoupled content authoring pipeline so curriculum team can update without engineering deploys

2.3 Screen Rendering Model
Each module is defined as a JSON 'screen graph' fetched from the Content Service. The Screen Renderer interprets this graph and instantiates the corresponding React component for each screen type, enabling curriculum updates without redeploying frontend code for content-only changes.
// Example screen graph node (simplified)
{
  "screenId": "1.3",
  "type": "GuidedExplanation",
  "loRefs": ["LO-02"],
  "layout": "clock-center-character-left",
  "narrationAudio": "cdn://audio/m1/s3_hour_hand.mp3",
  "subtitleText": "See the short, chubby hand? That's the hour hand!",
  "clockConfig": { "mode": "animated", "highlightHand": "hour", "startTime": "03:00" },
  "transitions": { "next": "1.4", "skipAllowed": false }
}

2.5 Audio-Sync Narration Controller
Narration audio must remain synchronized with on-screen highlights (e.g., highlighting the minute hand exactly when the narrator says 'minute hand'). This is achieved via a timestamped cue-track approach:
// Cue track format (JSON, stored alongside audio file)
{
  "audioFile": "s3_hour_hand.mp3",
  "durationMs": 4200,
  "cues": [
    { "atMs": 0,    "action": "highlight", "target": "hourHand" },
    { "atMs": 1800, "action": "pulse",     "target": "hourHand" },
    { "atMs": 3000, "action": "subtitle",  "text": "That's the hour hand!" }
  ]
}
The AudioSyncController listens to Howler's playback position (polled at 60fps via requestAnimationFrame) and dispatches cue actions to the Clock Engine and Subtitle component.
If audio fails to load (offline/error), cues fire on a timer fallback using durationMs to preserve pacing.

3.2 Microservice Breakdown
3.2.1 Auth Service
Handles account creation for parents/teachers; child profiles linked to guardian accounts (no direct child PII collection beyond first name/avatar)
Implements COPPA-compliant verifiable parental consent (VPC) flow
Issues short-lived JWT access tokens (15 min) + refresh tokens (30 days, rotated)
Supports SSO for school districts via Google Classroom / Clever / ClassLink

3.2.2 Progress Service
Stores per-student state: module completion, LO mastery scores, XP, level, badges, stars
Exposes endpoints: GET /progress/{studentId}, POST /progress/{studentId}/events
Idempotent event ingestion (client may retry on flaky connections — events de-duplicated by clientEventId)
Computes star ratings server-side to prevent client tampering

3.2.3 Content Service
Serves versioned 'screen graph' JSON for each module
Supports content staging/preview for curriculum team via Admin CMS
Implements content versioning so in-progress student sessions aren't disrupted mid-module by live edits
Returns localized content bundles based on Accept-Language header (future i18n)

3.2.4 Adaptive Engine
Consumes real-time answer events; maintains rolling performance window (last 5 answers) per LO
Outputs difficulty tier (Scaffolded / Standard / Extended) consumed by Content Service question selector
Stateless compute with Redis-backed session state for low latency (<50ms decision time)

3.2.5 Analytics Pipeline
Ingests granular interaction events (screen views, answer attempts, hint usage, time-on-screen)
Feeds learning efficacy dashboards (Section 9 of PRD) and curriculum iteration reports
PII-scrubbed before long-term storage; aggregated reporting only

7. Security, Privacy & Compliance
7.1 Child Data Privacy Compliance
🔒 COMPLIANCE MANDATE
The platform must comply with COPPA (USA), GDPR-K / UK GDPR Age Appropriate Design Code (UK), and equivalent child-data protection regulations in Australia (Privacy Act) and India (DPDP Act) for any user under 13. No directly identifying information is collected from children; all account management occurs at the guardian/teacher level.

Requirement
Implementation
Verifiable Parental Consent
Email + payment-method verification or signed consent form before child profile activation
Data Minimization
Child profiles store only: display name (or generated nickname), avatar selection, locale, progress data
No Behavioral Advertising
Zero third-party ad SDKs; no cross-app tracking identifiers
Data Retention
Inactive accounts (24 months) auto-purged with guardian notification
Right to Deletion
Guardian-initiated full account + data deletion via portal, fulfilled within 30 days
Data Residency
Regional data storage options (US, EU, APAC) for school district compliance
Third-Party Processors
All sub-processors (hosting, analytics) vetted and listed in privacy policy

7.2 Application Security
All traffic over TLS 1.3; HSTS enforced
JWT signing via RS256; key rotation every 90 days
Rate limiting on all public endpoints (100 req/min per IP for unauthenticated)
Input validation via JSON Schema on all API requests (Fastify schema validation)
Dependency scanning (Snyk/Dependabot) integrated into CI
Regular penetration testing (annual, plus pre-launch)
Content Security Policy (CSP) headers restricting script sources to self + approved CDN
